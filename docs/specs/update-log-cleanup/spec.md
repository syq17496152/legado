# spec — updateLog.md 面向用户重写

## Intent
updateLog.md 是发版交付物的用户可见部分，必须可读、可信、面向用户。本次将 125 个批次条目重构为按天合并的用户视角日志。

## Scope
- **改**：`app/src/main/assets/updateLog.md` 全量重写（按天合并、去黑话、去重、删纯开发条目）
- **改**：`docs/project-rules/version-delivery-sync.md` 格式章节（同日多批合并约定 + 分节格式）
- **改**：`docs/INDEX.md` 登记 spec
- **不改**：任何代码；不改 `## cronet版本:` 头格式；不改发布脚本（按天合并后其提取逻辑天然完整）

## Requirements
- R1 条目粒度：一个日期一个条目，标题格式 `**YYYY/MM/DD**`（发布脚本正则 `\*\*(\d{4}/\d{2}/\d{2})` 必须继续命中）
- R2 结构：条目内用 `### 修复` / `### 新增` / `### 优化` / `### 说明` 分节
- R3 语言：面向用户——描述现象与效果，禁止竞态/幂等/缓存键/类名/异常名/组件名等内部术语；允许保留功能名（书源/订阅源/TTS/AI 分镜/暗夜紫等）
- R4 去重：同一问题多批反复修复的，合并为一条最终态；同日重复条目（09/03 重复段）删除
- R5 删除纯开发事务：构建提速、JDK 升级、日志/测试基建、"沉淀规范"类；诊断日志类仅保留用户可感知的（如日志管理功能）
- R6 保留全部用户可感知功能与修复，覆盖 2026/07/04 → 09/12 全部日期
- R7 敏感词合规：不出现源名称/域名/URL/cookie（output-safety.md）

## Scenarios
### Scenario: 发布脚本提取当日条目
- WHEN `publish_release.py` 以 `**YYYY/MM/DD` 提取发布日条目
- THEN 当日唯一条目整体被提取，无同日多批丢条目问题

### Scenario: 用户启动弹窗/关于页阅读
- WHEN 非调试包启动或关于页打开更新日志
- THEN 按天倒序展示、分节清晰、无内部术语

## Approach
纯文本重构，无代码。旧文件由 Git 历史兜底（app assets 在版本控制内），不另建备份。

## Drawbacks
- 历史细节有损（实现机制描述被删除）——接受：日志面向用户，机制记录在 spec/commit 里
- 后续若忘记"同日合并"约定又追加新批标题，回到旧问题——兜底：version-delivery-sync.md 已写死该约定
