# updateLog.md 面向用户重写（update-log-cleanup）

## 状态
**已完成（2026-09-12）**

## 概述
`app/src/main/assets/updateLog.md` 是发版时直接给用户看的更新日志，同时被三个消费方使用：
1. 关于页「更新日志」全量渲染（AboutFragment）
2. 非调试包启动时弹窗全量展示（MainActivity:2207）
3. `scripts/publish_release.py` 按 `**YYYY/MM/DD` 正则提取**当日第一条**作为 GitHub Release body

存量问题（用户裁决：内容杂乱、冗余、阅读性差）：
- 70 天内堆了 **125 个批次条目**（`**日期（第N批·标题）**`），一天最多 11 批；批次编号还有两轮循环重叠（09/06-09/07 两套"第一批~第六批"）
- 大量"修复上一批自己引入的 Bug"的条目，同一问题跨批反复登记（如 TTS 缓存键在 20/21/23 批各修一次）
- 条目充满开发黑话（竞态/幂等/缓存键/Compose/ANR/LRU/类名/异常名），违反 version-delivery-sync「面向用户通俗语言」原则
- 发布脚本缺陷暴露：同日多批时 Release body 只取当日第一条，后续批次被静默丢弃
- 体积 0.3MB / 1647 行，启动弹窗全量怼给用户

## 变更点
- 按**天**合并：一天一个 `**YYYY/MM/DD**` 条目（保留发布脚本依赖的标题格式），同日内 修复/新增/优化/说明 分节去重
- 语言全面去黑话：只保留用户可感知的现象与效果，删除实现机制与内部术语
- 纯开发事务条目删除（构建提速/JDK 升级/测试稳定性/"沉淀前端规范"等）；同系列碎片条目（界面字号统一（一）~（九）等）压缩为一条概括
- 重复修复链合并为一条最终态描述
- `## cronet版本:` 头保留；volume 0.3MB → 约 70KB

## 后续工作流约定
- 后续同日多批变更时，**合并写进当天唯一条目**（不再追加新批次标题），保证发布脚本提取完整
- version-delivery-sync.md 格式章节已同步此约定
