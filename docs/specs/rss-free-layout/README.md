# 订阅源「自由」布局（智能相册网格）

> 状态：🟡 L1 已完成（代码落地 + 编译通过 + 单测 13/13 通过 + **测试包已产出**），**L2/L3 真机验证受阻**（无设备）
> 创建：2026-09-11｜路径：扩展路径（标准化）
> 关联既有 spec：`rss-classic-layout-align`（布局枚举现状）、`rss-image-load-optimization`（图片加载链路/缓存基础设施）

## 一句话目标

在订阅源文章列表现有 5 种样式（列表 / 单列 / 双列 / 瀑布 / 三列）之后新增第 6 种「自由」：
**同一行所有图片高度相等、宽度按原图宽高比分配、整行精确撑满可用宽度**，即业界所称 Justified Photo Grid / Ad-hoc Photo Grid（Google 相册、Flickr、iCloud 网页端同款）。

## 核心能力

| 能力 | 说明 |
|------|------|
| 等行高流式网格 | 行内**图片区**统一高度 `H_img`，第 i 张宽度 = `H_img × ratio_i`，行宽误差 0px（末位补偿） |
| 原比例不变形 | 布局框比例 = 图片原始比例，视觉无拉伸 |
| 动态行列 | 行内张数由贪心装填 + 目标行高逼近决定（1–4 张，横屏 1–6 张） |
| 保留标题与时间 | 与既有 5 种样式视觉语言一致；文字块高度为**编译期常量**，故 `rowHeight = H_img + T` 不破坏「行高统一 + 整行撑满」（AD-08） |
| 尺寸供给层 | `origin@link` 为键的三级 ratio 缓存（内存 → 磁盘 KV → 异步解码），布局路径零阻塞 |
| 稳定回填 | 可见区域已布局行不抖动（脏标记延迟重排）；首屏 gating 一次成型 |
| 零数据库迁移 | 复用 `CacheManager` KV 表，不动 Room schema |
| position 语义不变 | Adapter 仍是 `List<RssArticle>`，播放器/图库位置记忆、DiffUtil 全部零改动 |

## ✅ 两项裁决已定稿（2026-09-11 用户裁决）

| 编号 | 议题 | 裁决结果 |
|------|------|---------|
| **AD-08** | 标题/时间如何承载 | **方案 B — 图下固定文字块**，`TEXT_BLOCK_HEIGHT = 46sp`（`dimens.xml` 单源，同一配置下为常量）。与现有 5 种样式视觉语言一致；代价为一屏图片数减少约 25–30%。方案 A（图上遮罩）已评估否决（窄格子文字不可读） |
| **AD-09** | 极端比例图（全景/长条） | **策略 X — 钳制裁边**。ratio 钳制到 `[0.4, 3.0]`，超出部分 `CENTER_CROP`。保住「每行撑满 + 行高统一」不变式；代价为 5:1 全景图约损失 40% 宽度（真实 RSS 配图多数落在 0.5–2.0，属少数情况）。策略 Y（保真留白）已评估否决，回退路径保留 |

> 两项均只影响**单点常量与分支**（`TEXT_BLOCK_HEIGHT` 取值、计算器两处分支），若实测需调整，改常数即可。

## 五种样式现状盘点（决策依据）

| style | 名称 | 图片尺寸 | 图文关系 | 圆角实现 |
|-------|------|---------|---------|---------|
| 0 | 列表 | 固定 110×68dp | **左右**（文左图右） | `FilletImageView` 12dp |
| 1 | 单列 | 宽 match × 固定高 220dp | 上下 + 分隔条 | `FilletImageView` 12dp |
| 2 | 双列 | 宽 match × 固定高 272dp | 上下 | `FilletImageView` 12dp |
| 3 | 瀑布 | 宽=列宽（固定）× **高=列宽÷原比例** | 上下 | **`CardView`** 12dp `clipToOutline` |
| 4 | 三列 | 宽 match × 固定高 182dp | 上下 | `FilletImageView` 12dp |

- **五种样式无一种为纯图**，全部带标题 + 时间 → 自由布局保留文字（AD-08）。
- 1/2/4 为固定高度 → 图片必然被 `centerCrop` 裁切，这是「竖图被压缩/留白」的根源。
- 只有 3（瀑布）按原比例算图高，且因高度动态改用 `CardView` → 自由布局沿用该方案。

## 关键结论（可行性）

**技术上完全可行，且不需要引入第三方依赖。**

- 算法本身是 O(n) 贪心装填，无难点；难点在 **Android 侧「布局时拿不到图片尺寸」** —— 本项目尤其突出：列表主查询 `flowByOriginSort` 出于 CursorWindow 2MB 限制**不 select image 列**，image URL 需异步单行查库，ratio 更需解码后才知。设计以「尺寸供给层 + 乐观布局 + 延迟回填 + 首屏 gating」四件套解决。
- 选定 **自定义 `RecyclerView.LayoutManager`（预计算 Rect 表）**，而非「行合并 ViewGroup」，决定性理由是 **position 语义不变** → 现有播放器/图库联动、DiffUtil、分页加载全部零改动。
- 参考 500px/greedo-layout-for-android（MIT）算法思路自研 Kotlin 实现，**不引入该依赖**（Maven 托管在 GitHub raw、2022 年后停更、footer 会被当图片摆进行内）。

## 已知取舍（不可能三角，必须接受其一）

「保持原比例 + 整行撑满 + 行高在合理区间」三者对**最后一行**和**极端比例图**无法同时满足：

| 场景 | 取舍 |
|------|------|
| 最后一行剩 1–2 张装不满 | 牺牲「撑满」：`H_img` 取 `TARGET_ROW_HEIGHT` 左对齐、右侧留白（Google 相册同款）。拉伸会让单图占满整屏，观感更差 |
| 单张全景图（ratio > 3.0）/ 长条图（ratio < 0.4） | 牺牲「不裁剪」：ratio 钳制到 `[0.4, 3.0]` + `CENTER_CROP` 裁边（AD-09 策略 X 定稿；策略 Y 保真留白已否决） |
| ratio 未知（首次加载、解码失败） | 用源级中位数（无数据则 4:3）估算布局，真值到达后按脏标记规则重排 |
