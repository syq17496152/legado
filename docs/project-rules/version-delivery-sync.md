# 版本交付同步规范（version-delivery-sync）

> **任何涉及代码变更的任务完成后，必须同步更新 `assets/updateLog.md`。禁止只改代码不写更新日志！**
>
> **触发场景**：任何代码变更任务（新功能/Bug修复/优化/重构）完成后
> **来源**：从 AGENTS.md 提取为独立子规范

## 同步清单

| 变更类型 | 必须同步的文件 | 说明 |
|----------|--------------|------|
| **任何代码变更** | `app/src/main/assets/updateLog.md` | 顶部追加日期条目，写明用户可感知的变更内容 |
| **文档变更** | `docs/INDEX.md` | 更新 spec 状态标记 |
| **架构变更** | `docs/project-flow/` 相关文档 | 同步架构说明 |
| **Skill 变更** | `.trae/skills/` 相关 SKILL.md | 同步能力说明 |

## updateLog.md 格式（2026-09-12 重构后）

```markdown
**YYYY/MM/DD**
### 修复
- 现象 + 效果（面向用户，非技术细节）
### 新增
- ...
### 优化
- ...
```

**条目位置**：追加在 `## cronet版本:` 行之后、已有条目之前。

**条目粒度（重要）**：**一个日期只有一个条目**。同日多批变更时，把新内容合并进当天已有条目的对应分节（`### 修复`/`### 新增`/`### 优化`），**禁止**追加 `（第N批）` 等新标题——`publish_release.py` 按 `**YYYY/MM/DD` 提取"当日第一条到下一条目之间"作为 Release body，一天多条会导致后面的批次被静默丢弃；且启动弹窗/关于页会全量展示该文件，批次碎片化会直接伤害可读性。

**内容原则**：
- 面向用户，用通俗语言描述可感知的变化（现象 + 效果）
- 禁止内部术语（竞态/幂等/缓存键/类名/异常名/组件实现名等）
- 纯开发事务（构建提速、依赖升级、内部日志治理、"沉淀规范"类）不写入
- 一个变更点一条，不合并；重复修复链写最终态一条

## 更新时机

> **编译前更新**，不是交付阶段！

- 在代码变更完成、准备编译前，先更新 updateLog.md
- 然后再执行编译命令
- 禁止在交付阶段才补写 updateLog.md

## updateLog 更新方法论（强制）

> **更新日志必须基于真实代码变更分析生成，禁止仅对已有日志条目做文字合并。**

### 三步流程

```
Step 1: 代码变更分析 → Step 2: 功能提炼与去重 → Step 3: 面向用户重写
(git diff提取真实变更)   (合并同类项+识别遗漏)    (通俗语言+可感知描述)
```

### Step 1: 代码变更分析

用 git diff 提取当日所有真实代码变更，逐文件审计：

```bash
# 获取当日提交范围
git log --oneline --since="YYYY-MM-DD" --until="YYYY+1-MM-DD" --all --format="%h %ai %s"
# 获取源码变更统计
git diff <first_commit>..<last_commit> -- "*.kt" "*.java" --stat
# 获取完整diff（用于逐文件分析）
git diff <first_commit>..<last_commit> -- "*.kt" "*.java"
```

**必须分析的范围**：仅 `app/src/main/` 下的源码文件，忽略 docs/test/脚本等。

### Step 2: 功能提炼与去重

对每个变更点提取用户可感知的功能变化，并执行去重：

| 去重场景 | 处理方式 |
|----------|---------|
| 同一功能多次提交 | 合并为一条，取最终效果描述 |
| 同根因不同表现（如同一DB限制导致卡顿+崩溃） | 合并为一条，描述完整影响范围 |
| 一个大功能拆多个小提交 | 合并为一条，描述整体功能 |
| 不相关的独立变更 | 各自独立成条 |

**关键：检查是否有代码变更被遗漏**——对照 git diff 文件列表，确认每个变更文件都有对应的日志条目。

### Step 3: 面向用户重写

| 要求 | 说明 |
|------|------|
| 通俗语言 | 用户能理解"修复了什么问题"而非"改了哪个类" |
| 可感知 | 描述用户能看到/体验到的变化 |
| 分类排列 | 按功能域排列：数据库/网络/图片/视频/规则解析等 |
| 完整性 | 不遗漏任何用户可感知的变更 |

## 反模式

❌ 改代码不写 updateLog.md
❌ updateLog.md 只写"优化代码，修复问题"无具体内容
❌ 新功能上线但用户不知道
❌ tasks.md 全部完成但 updateLog.md 未更新
❌ 在交付阶段才补写 updateLog.md（应在编译前）
❌ 仅对已有日志条目做文字合并/去重，不分析真实代码变更（铁证：2026-07-15 用户批评"我要的不是文字上的合并，而是基于真实变更的完整分析整合"）
❌ 遗漏代码变更（必须对照 git diff 逐文件确认每个变更都有对应日志条目）

## 文档同步检查（强制）

> **任务完成前，必须检查所有相关文档是否更新到最新状态。**
> **来源**：2026-07-17 用户批评"文档什么的也都更新到最新状态了么？"

### 文档同步检查清单

| 文档 | 检查内容 | 触发条件 |
|------|---------|---------|
| updateLog.md | 是否有本次代码变更的条目 | 任何代码变更 |
| issues-found.md | Issue状态是否最新（待修复→已修复） | Bug修复任务 |
| tasks.md | Phase是否勾选完成 | OpenSpec任务 |
| INDEX.md | 是否引用新增子规范 | 新增子规范 |
| project_memory.md / ai_memory_main.md | 是否记录用户反馈和决策（本项目用 .trae/memory/ai_memory_main.md） | 任何用户反馈 |

### 检查时机

- 任务完成前（编译安装后、AskUserQuestion确认前）
- 用户询问"是否都完事了"时

### 反模式

- ❌ 只改代码不更新文档（用户批评"文档什么的也都更新到最新状态了么？"）
- ❌ tasks.md 所有Phase未勾选但声称任务完成
- ❌ issues-found.md 状态未回填
- ❌ 新增子规范未在INDEX.md和AGENTS.md引用
